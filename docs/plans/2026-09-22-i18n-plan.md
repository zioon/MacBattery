### 1.5 语言列表

| 语言 | 标识 | 角色 | 说明 |
|---|---|---|---|
| 简体中文 | `zh-Hans` | **默认 / 开发语言** | 资源文件的值 = 现有中文原文，保证回退后与今天逐字一致 |
| 英语 | `en` | 首批 | |
| 繁体中文 | `zh-Hant` | 第二批候选 | 由 zh-Hans 转换成本低；不加则 zh-Hant 系统回退到简体 |

**系统语言自动匹配规则**（首次启动、`language == .system`）：

1. 取 `Locale.preferredLanguages`（按优先级排序）
2. 逐项归一化：`en-*` → `en`；`zh-Hans-*` / `zh-CN` / `zh-SG` → `zh-Hans`；`zh-Hant-*` / `zh-TW` / `zh-HK` → `zh-Hant`
3. 命中支持列表即采用；**全部不命中 → 默认语言 `zh-Hans`**

> **决策点 B**：默认（回退）语言取 `zh-Hans` 还是 `en`？
> **建议 `zh-Hans`** —— 现有文案、README、CHANGELOG 全为中文，既有用户升级后看到的界面与今天**逐字相同**，是「不破坏现有功能」最直接的体现。改选 `en` 的代价：全部中文用户的回退目标变为英文。

## 3. 引擎设计

### 3.1 三级回退链

```
L("chart.series.voltage")
  → ① 选中语言表（en）       命中 → "Voltage V"
  → ② 默认语言表（zh-Hans）  命中 → "电压 V"          ← 翻译缺失时的回退
  → ③ 键名本身 "chart.series.voltage"                ← 永不崩、不显示空白
     + DEBUG 下 assertionFailure / 记录到 os_log
```

实现要点：
- 启动时把 `<lang>.lproj/Localizable.strings` **一次性读成 `[String: String]`**（`NSDictionary(contentsOf:)`），与默认语言表合并成一份「有效表」。查表退化为字典命中，**每次取文本零 Bundle 查询、零 IO**。
- `L()` 命中失败时回退到键名，**绝不 `fatalError`** —— 即使 CI 打包漏了资源 bundle，最坏是显示键名，而不是崩溃。
- 语言切换只需重载有效表（毫秒级），无需重启、无需重建进程。

### 3.2 运行时切换（不重启）

- `AppLanguage`：`.system / .zhHans / .en`，存 `UserDefaults` 键 `MacBattery.Settings.language`，由 `SettingsStore` 统一 `commit()`（与现有 `size/corner/tdp/passthrough` 同一条持久化路径）。
- `LocalizationManager: ObservableObject`，`@Published private(set) var language`：
  - SwiftUI 视图持有它 → 语言变化触发 `body` 重算 → 自动重绘；
  - `NSMenu` / `NSWindow.title` / `NSAlert` 是命令式 API，需在语言变化时显式刷新：挂到 `SettingsStore.onChange`（已有回调）→ 调 `menuController.rebuild()` + 重设三个窗口标题。
- 不使用 `AppleLanguages` 写入、不要求重启 —— 进程内自行选 bundle，行为可预期、可单测。

### 3.3 SwiftUI 铁律（最容易做错的一点）

```swift
Text(L("settings.title"))     // ✅ L() 返回 String → Text(String) 按字面渲染
Text("MacBattery 设置")        // ❌ 字面量走 LocalizedStringKey → 查 Bundle.main + AppleLanguages，绕过语言选择
```

`L()` 返回值一律是 `String`，因此 `Text(...)` 走 `init(_ content: some StringProtocol)`（**不参与本地化**），正确。反之任何遗留的中文字面量都会走另一条路，切语言后**部分文案不变**——这类 bug 肉眼极难发现，必须靠 CI 拦截（见 5.2）。

## 4. 复数 / 日期 / 数字 / 货币 / 布局

### 4.1 复数形式（`.stringsdict`，4 个键）

| 键 | zh-Hans | en（one / other） |
|---|---|---|
| `chart.summary.samples` | `样本 %d 个 · 查看最近 %@` | `%d sample · last %@` / `%d samples · last %@` |
| `health.unit.cycles` | `%d 次` | `%d cycle` / `%d cycles` |
| `duration.seconds` | `%d 秒` | `%d second` / `%d seconds` |
| `duration.minutes` | `%d 分钟` | `%d minute` / `%d minutes` |

- 中文只有 `other` 一类；英文需要 `one` / `other`。俄语/阿拉伯语等多类语言后续加语言时**自动被这套机制覆盖**，无需改代码。
- `duration.hours` / `duration.days` 用 `%.1f`，英文 "1.0 hours" 可接受，不入 stringsdict（避免无谓复杂度）。
- 不引入 `.xcstrings`（Xcode 15 的 String Catalog）：本项目由 SwiftPM 构建、CI 无 Xcode 编译资源流程，`.lproj` + `.strings/.stringsdict` 是最可靠的形态。

### 4.2 数字

现状 `String(format: "%.1f", v)`、`String(format: "%.0f", v)`（`ChartAxes.formatY/fmtVal`、HUD、指标 format）**无视区域**：德语/法语应显示 `58,2`。改为 `L10n.number(_:decimals:)`，内部 `NumberFormatter`。

**性能红线**：`PowerHUDView` 每秒刷新、图表每帧绘轴标签，**禁止在 `body` / 绘制路径里新建 `NumberFormatter`**（单次构造微秒级、每帧数十次会明显掉帧）。方案：`Formatters` 内 `static` 缓存 formatter，仅在语言切换时失效重建。

### 4.3 日期

3 处硬编码 `dateFormat`：`PowerChartView.swift:711-717`、`BatteryHealthChartView.swift:550-556`、`ChartHover.swift:22-28`。改为 `setLocalizedDateFormatFromTemplate`，让 12/24 小时制与日期顺序随区域：
`jm`（时:分）/ `jms`（时:分:秒）/ `MMdj`（月日 时:分）/ `Md`（月日）。
**注意**：12 小时制（`en_US`）下 `3:45 PM` 比 `15:45` 宽约 40%，图表底部 `bottomPad = 28` 的固定留白与刻度密度需复测。

### 4.4 区域对象（Locale）选谁

**建议数字/日期跟随"应用语言"派生出的 Locale**（`en` → `en_US`、`zh-Hans` → `zh_CN`），`.system` 时用 `Locale.current`。理由：应用内切到英文后，图标仍用 `Locale.current` 会出现「英文文案 + 系统区域数字/日期」的混合，与 macOS「每应用语言」的既有心智一致。

### 4.5 货币

**本应用当前没有任何货币展示**（无价格、账单、金额、付费项）——要求中的货币部分**不适用**。仅在 `Formatters` 预置 `L10n.currency(_:code:)`（`NumberFormatter.currency`，`locale` 随语言）以备将来，**不接任何调用点**，不为此造需求。

### 4.6 文本长度差异 → 布局风险点（按严重度）

| # | 位置 | 风险 | 对策 |
|---|---|---|---|
| 1 | `SettingsView.swift:79` `.frame(width: 340)` + `SettingsWindowController.swift:18-19` 用 `hosting.fittingSize.height` **只算一次** | 英文说明变长换行 → 高度不够被截断；切语言后高度**不更新** | 改 `minWidth/idealWidth` + 语言变化时重算 `fittingSize` 并 `setContentSize`；窗口改 `.resizable` 兜底 |
| 2 | 图表图例（7 项 + 数值）与底部工具条（4–5 个时间窗 + 全部 + 重置数据 + 2 段说明）在 640pt 最小宽下 | 英文标签更长（`Charging W`/`Voltage V`/`Current A`）→ 挤压/截断 | 英文用短标签（`Batt/Sys/Chg/CPU/RAM/V/A`）；图例由单行改为可换行布局。**注意 macOS 12 无 `ViewThatFits`（13+）**，需手写两段 `HStack` 或按语言选布局 |
| 3 | 挂件 `PowerHUDView` 底盘固定 58×58，`.fixedSize()` | 中文 `已用`（≈17pt）→ 英文 `Used ` 更长，加上 `12:34` 会撑破底盘 | 英文用更短的中性词或符号前缀（如 `↑0:45` / `↓12:34`）；前缀必须进资源文件，才能逐语言单独调 |

## 5. 回退机制与可扩展性

### 5.1 键名一致性靠测试强制（不是靠人记）

`LocalizationTests` 断言：

1. **键集对齐**：`en` 的键集 ⊇ `zh-Hans` 的键集，且差集为空 —— 新增语言/新增文案漏翻译**直接让 CI 红**（运行时仍回退中文，不会崩）。
2. **回退链**：构造「en 缺 key」的表，断言 `L(key)` 返回中文值；再构造两表都缺，断言返回键名而非空白。
3. **系统语言匹配**：`zh-Hans-CN`/`zh-CN`→zh-Hans、`zh-Hant-TW`→zh-Hant（未支持时→zh-Hans）、`en-GB`→en、`ja-JP`→默认。
4. **占位符一致**：同一键在各语言里的 `%d`/`%@` 数量与位置一致（防止英文译文漏掉一个参数导致 `String(format:)` 出乱码）。
5. **格式化区域化**：`en_US` 下 `L10n.number(58.2, 1) == "58.2"` vs `de_DE` 下 `"58,2"`；12/24 小时制模板生效。

新增语言 = 加一个 `.lproj` + 在 `AppLanguage.supported` 注册一行，**测试自动覆盖、UI 自动出现选项**。

### 5.2 零硬编码守护

`Scripts/check_hardcoded_strings.py`（与现有 purity guard 同风格，CI 里 `exit 1`）：

### 5.3 新增文案的标准流程

1. 代码里写 `L("new.key")`

## 10. 实施记录（2026-09-22 执行，与方案有 5 处偏离，均已落地）

评审结论：A 不本地化 os_log｜B 默认 `zh-Hans`｜C 语言 = 中文 + 英文｜D 版本按 1.2.0（**未动版本号**，条目进 `[Unreleased]`）｜E 语言入口在设置窗口顶部。

| # | 方案原文 | 实施 | 理由 |
|---|---|---|---|
| 1 | 复数用 `.stringsdict` | 改为 `<key>.one` / `<key>.other` 后缀键 | Foundation **未公开 CLDR 复数规则 API**（无法自行判定类别），而 `.stringsdict` 的解析挂在 bundle 内部行为上；本项目无本地工具链、CI 是唯一验证通道，那种「解析失败 → 界面显示 `%#@count@` 乱码」的失败模式无法在本地验证。自判类别 + 后缀键完全可单测，且未来加 `few`/`many` 只需补键并扩展 `PluralCategory.select` |
| 2 | `hud.placeholder` 键 | 改名 `common.placeholder`（挂件 / 两张图的图例三处共用） | 三处占位符语义相同，按「同一文案只有一个键」收敛 |
| 3 | 键清单 96 条 | 实际 **104 条** | 补了方案漏掉的 `hud.voltage_amps.placeholder`（`--V · --A`）、`health.unit.mah.short`（`mAh`）、`health.unit.pct.sign`（`%`）、语言自名 3 条（`language.system/zh-Hans/en`，各语言文件里刻意相同、勿翻译） |
| 4 | 设 `minWidth/idealWidth` 抗文本变长 | 保持固定 `width: 340`，改为给长说明文字加 `.fixedSize(horizontal: false, vertical: true)`（换行而非截断）+ 语言切换时**重算窗口高度** | 换行 + 高度重算已足够覆盖英文变长；固定宽度避免动到既有布局比例，风险更小 |
| 5 | 仅 1 个 CI 守护脚本 | 增到 **2 个** | 第二个（`check_localization_keys.py`）覆盖首个脚本覆盖不到的三类问题：漏翻译、格式占位符漂移、**代码引用了不存在的键**（`swift test` 查不出「键被用错」这类问题） |

### CI 抓到、本地无法发现的 2 个真问题（都在 manifest/编译期）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | `swift test` 在**解析 manifest 阶段**即失败：`manifest property 'defaultLocalization' not set; it is required in the presence of localized resources` | **SwiftPM 强制要求**：target 含 `*.lproj` 资源时 `Package(...)` 必须声明 `defaultLocalization` | `Package.swift` 加 `defaultLocalization: "zh-Hans"`（与 `AppLanguage.fallback` 一致） |
| 2 | 编译报 `LocalizedFormat.swift:40: cannot call value of non-function type 'Date'` | 便捷重载的形参叫 `date`，**遮蔽了同名方法**，`date(value, …)` 被当成「调用该参数」 | 形参改名 `value`，内部调用加 `Self.` 前缀（两个重载都改） |

> 教训：本项目**没有本地 Swift 工具链**，`defaultLocalization` 这类 manifest 级约束只有 CI 能发现 —— 所以「先 `workflow_dispatch` 跑绿、再移动 tag 发布」这个顺序是必要的，直接打 tag 会白留一条失败的 run。

### 本次实证的环境事实（与发布流程相关）

- `git push` 在 Agent 会话里**静默全阻塞**：`1>`/`2>` 都是 0 字节、exit 128，`--dry-run` 亦然（`ls-remote`/`fetch` 正常）。改用 **Git Data API**（`gh api` + `POST /git/trees` → `/git/commits` → `PATCH /git/refs/heads/main`）逐个重建提交，tree 与本地**完全一致**（`git rev-parse <sha>^{tree}` 比对 `dffd6f8c…` 相同）；建 tag 与移动 tag 也走 `/git/refs`，**能正常触发 tag 的 push 事件**。
- 远端 SHA 与本地 SHA 不同（committer/timestamp 变），发布后已 `fetch` + `reset --hard` 对齐本地，并把本地 tag 重新指向 `4750608`。
- 版本一致性校验通过：`AppVersion.fallback = 1.2.0` = tag = `CHANGELOG.md` 的 `## [1.2.0]`。
