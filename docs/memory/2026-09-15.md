## MacBattery 项目通读（目标 / 架构 / 发布流程）

- 定位：macOS 置顶 HUD 挂件，显示电量圆环、充电功率、整机功率、CPU/RAM，附历史图表与电池健康。SwiftUI + SPM，零第三方依赖，目标 macOS 12+，Intel 机型优先。
- 代码结构（约 4500 行）：
  - `Sources/MacBattery/` 15 个 Swift 文件：入口 `main.swift`；数据层 `Battery.swift` / `SystemPower.swift` / `SMC.swift`；中枢 `PowerMonitor.swift`（0.5s 后台串行队列采样）；持久化 `PowerLogger.swift` / `BatteryHealthLogger.swift`；UI `FloatingPanel.swift` / `PowerHUDView.swift` / `SettingsView.swift`；图表 `PowerChartView.swift`(915) / `BatteryHealthChartView.swift`(704) 及两个 PanelController；更新 `Updater.swift`。
  - `Sources/MacBatteryHelper/main.swift`：root 守护，每秒读 SMC 写 `/tmp/macbattery_power.json`。
  - `Sources/SMCBridge/`：C 实现 `SMC.c` + `SMC.h` + modulemap，保证 80 字节协议帧布局。
- 整机功率三级回退：SMC 直读（PSTR/PDTR/PCHC/PSYS/PWRS）→ root helper 的 JSON → `TDP × CPU曲线 + 平台基础功耗` 估算。
- 充电状态判定优先级：插拔事件后 2.5s 窗口内用 IOPS 即时状态 → 其余时间以 `pmset -g batt` 为权威（含 finishing charge）→ 失败再退回 IOPS/IsCharging/电流方向。
- 发版流程：改 `AppVersion.fallback` + CHANGELOG → `git push` tag `vX.Y.Z` → GitHub Actions（macos-14）`swift build -c release --arch arm64 --arch x86_64` 通用二进制 → 组装 `dist/MacBattery.app`（PlistBuddy 用 tag 覆盖版本号）→ `hdiutil` 出 DMG → `gh release create`。应用内 `UpdateChecker` 查 `api.github.com/repos/zioon/MacBattery/releases/latest` 比对版本并下载 DMG 到「下载」。

### 加锁设计（本批最高风险，已固化）
三个类型各一把 `private static let lock = NSRecursiveLock()`（macOS 12 不能用 `OSAllocatedUnfairLock`）。三条铁律：**① 锁绝不跨 `pmset` 子进程持有**（否则主线程从"等子进程 5s"变成"等锁 5s"，等于白改）**② 不允许两把锁嵌套**（故 `SystemPower.watts()` 刻意不加锁，只在 `cpuUsage()` 内保护 `lastCpuTicks`）**③ `chargingStatus()` 用显式 `lock()`/`unlock()` 而非 defer**（须在函数中途解锁），每条 return 都要配对解锁。
另：`chargingStatus()` 把原 `if sinceEvent<window, let io=…` 拆成"锁内暂存 `eventImmediate` + 锁外三分支"，主理人与 QA 各自独立验证了三分支等价性与 `pmsetCache = nil` 触发条件未漂移。

### 环境异常：本 worktree 的 refs/heads/workbuddy/* 被外部管控（重要）

- 现象：`git commit` 报成功（`[workbuddy/main-247e6f68 5fe8944]`），但**分支 ref 随后消失**——`refs/heads` 下只剩 `main`，`git rev-parse HEAD` 报"无提交"，`git branch -vv` 不列该分支。reflog 早先还有一条 `reset: moving to HEAD`。

- 推论：WorkBuddy 的 worktree 机制会移除该命名空间下的分支 ref。**在这里提交不会留下分支**，但提交对象会留在共享对象库里。
- 影响与应对：
  - 零数据损失——提交对象在、`main` 与 `origin/main` 未被触碰、工作树内容完好。
  - **本 worktree 与 `D:/Project/MacBattery` 共享同一对象库**（`git-common-dir` 指向它），所以提交对象直接在用户主仓库里，不需要传补丁。
  - 发布用「按 SHA 直接推」绕过本地 ref：`git push origin <sha>:refs/heads/main`（快进）+ `git push origin refs/tags/<tag>`。

### 环境异常的应对已固化

- 该 worktree 的 `refs/heads/workbuddy/*` **在派活前就已 unborn**（不是提交后才消失）。工程师若照常 `git add -u && git commit` 会产出**无父提交的 root commit**（曾产出废弃的 `668aefb`），推上去会覆盖历史。
- **正确做法（已验证）**：`git add -u` → `TREE=$(git write-tree)` → `NEW=$(git commit-tree "$TREE" -p <父SHA> -F msg)` → `git update-ref refs/heads/<保活ref> "$NEW"`。保活 ref 要**避开** `workbuddy/*` 命名空间（当前用 `refs/heads/batch2-pending-review`）。
- **推送用 SHA 直接推，绕开本地 ref**：`git push origin <sha>:refs/heads/main`（快进）+ `git push origin refs/tags/<tag>`。
